# GNOME Extension Review Guidelines

Local checklist for keeping this extension maintainable and acceptable for GNOME Shell review (it is not currently published to extensions.gnome.org, but the same bar applies).

## Lesson from a prior rejection (Containers Manager)

A sibling extension of this author (*Containers Manager*) was rejected on
review with the single sentence **"This code seems to be generated by AI."** and
pointed at two rules:

- [Extensions must not be AI-generated](https://gjs.guide/extensions/review-guidelines/review-guidelines.html#extensions-must-not-be-ai-generated)
- [Submissions require maintainership](https://gjs.guide/extensions/review-guidelines/best-practices.html#submissions-require-maintainership)

The clipboard was **not** the reason for that rejection; a `manual_review`
finding about `St.Clipboard.get_default()` is only a Shexli signal and remains
acceptable when clipboard use is the extension's explicit purpose and is
declared in `metadata.json`.

Key reading of the rule: GNOME does not ban AI as a development or learning
tool. It requires the author to be able to explain and justify every non-trivial
path. Submissions are refused for *signals* such as lots of useless code,
inconsistent style, non-existent APIs, prompt-like LLM comments, and other
typical generated-output patterns. The same signals are what the Best Practices
page calls out explicitly:

- `try/catch` around calls that normally do not throw;
- `typeof ... === 'function'` on guaranteed APIs;
- optional calls `foo?.()` on methods that are guaranteed to exist;
- defensive lifecycle flags such as `_destroyed` / `_enabled`;
- excessive compatibility code defending against many GNOME versions.

### How to act on this

1. Audit the whole extension against the Review Guidelines and Best Practices
   before any resubmission — do not just remove one or two `try/catch` blocks.
2. Remove the defensive constructs above unless the underlying operation can
   genuinely fail; justify each retained one.
3. Keep every used API real for the GNOME Shell version(s) declared in
   `metadata.json` (here: `["50"]`).
4. Cut verbose or obvious comments and duplicated abstractions.
5. Split `extension.js` when it grows past a size a reviewer can reasonably
   read; a smaller review surface reduces the "AI smell".
6. Test `enable` → `disable` → `enable`, reload, and login/logout for real.
7. Optionally do a hostile self-review pass (act as the EGO reviewer) on the
   final code before submitting.
8. Do not touch the clipboard code only to silence the Shexli warning.

## AI Usage

- AI assistance is acceptable, but the final code must be understood, reviewed, and maintainable by the developer.
- Do not submit pasted LLM output that contains unused abstractions, invented APIs, generic defensive code, or prompt-like comments.
- Every non-trivial code path should be explainable in GNOME Shell/GJS terms.

## Code Style

- Keep code small, direct, and consistent with existing GNOME Shell extension patterns.
- Avoid broad `try/catch` blocks unless a specific GNOME/GIO operation can reasonably fail and the recovery behavior is clear.
- Do not leave stale classes, unused settings, backup files, generated bundles, or old implementation copies in the source tree.
- Do not add comments that describe obvious code or serve as prompts to an LLM.
- Keep JavaScript and CSS lines at most 200 characters long.
- Keep `extension.js` limited to lifecycle wiring; put Shell-only components in
  `shell/` and GTK/Adw code in `prefs.js` or a dedicated preferences module.

## GNOME Shell Safety

- Do not use `Gio.DBus.session.add_filter()` in `extension.js`; it crashes GNOME Shell 50 devkit sessions (see `docs/VERIFICATION.md` §1.4).
- The extension uses one targeted async `Gio.DBusProxy` call to Authenticator's Search Provider; no global D-Bus filter and no notification interception.
- Do not import GTK or Adw in Shell runtime code (`extension.js` and `shell/`); those imports belong to `prefs.js` only. The Shell UI uses only St/Clutter/Pango.
- Each component owns its signals, timers and cancellable, and releases them
  in its own teardown. `disable()` destroys the popup and clears its reference.
- When a callable method creates a timeout, place removal of the previous
  source immediately before its replacement. Remove the focus idle on close.
- Clear account identifiers as well as rows during teardown.
- Track refresh ownership by request identity: an old request must not clear
  the ownership of a newer request in its `finally` block. Generation counters
  and row action tokens reject stale replies; they are not lifecycle booleans.
- Codes must never be written to GSettings, files, logs, or notifications.

## Security Model

- Authenticator is the single source of truth: accounts and codes are read only through its `org.gnome.Shell.SearchProvider2` service.
- `GetInitialResultSet` is the authoritative lock/availability gate; re-check it while the popup is open.
- Never call `GetResultMetas` with cached ids that the current availability check did not return.
- `metadata.json` declares `settings-schema` for **UI preferences only** (appearance, behaviour, shortcut). Account names, account identifiers, provider names and codes must never be written to GSettings, files, logs or notifications.

## Runtime Behavior

- The 1 s refresh timer runs only while the popup is open; it is removed on close.
- Codes are kept in memory only for revealed rows and dropped on copy and on popup close.
- Clipboard writes via `St.Clipboard.get_default().set_text()` are declared in `metadata.json` description.

## Packaging

- The extension UUID in `metadata.json` must match the installed directory name (`authenticator-companion@giaffa86`).
- Only `metadata.json`, `extension.js`, `prefs.js`, `stylesheet.css`, `shell/` and the schema XML are shipped; keep `tools/`, `docs/`, `scripts/`, `*.md` and generated bundles out of extension ZIPs by using an explicit runtime-file list; `.gitignore`
  alone does not control ZIP contents. Never include `gschemas.compiled`.
- The schema is compiled with `glib-compile-schemas` (the sync script does this); it holds UI preferences only.
- Verify with a nested GNOME Shell after significant `extension.js` changes (see `docs/VERIFICATION.md`).

## Official sources and maintainership

The [EGO Review Guidelines](https://gjs.guide/extensions/review-guidelines/review-guidelines.html)
are the publication rules. The [Best Practices](https://gjs.guide/extensions/review-guidelines/best-practices.html)
provide implementation guidance. [AI and GNOME Shell Extensions](https://blogs.gnome.org/jrahmatzadeh/2025/12/06/ai-and-gnome-shell-extensions/)
explains the review team's concerns.

The Best Practices ask AI tools generating extension files to include the
personal-use notice shown on that page. The author must understand JavaScript,
review the code and accept maintainership before manually removing that notice
for submission. Absence of the notice is not evidence of that review. An
assistant or a clean scanner result cannot certify the author's understanding
or guarantee EGO approval.

## 2026-10-20 audit remediation

- Reduced `extension.js` to lifecycle wiring and separated the Search Provider,
  popup controller and account row into `shell/` modules.
- Cleared cached account identifiers during popup destruction.
- Replaced the shared busy boolean with request ownership, so a stale refresh
  or tick cannot unlock a newer request after the popup is reopened.
- Placed periodic timer replacement next to creation and cancelled the deferred
  focus callback when the popup closes.
- Removed comments that repeated nearby code; retained explanations of the
  provider's lock limitations and asynchronous invalidation.
- Updated installation, nested-shell fixtures and packaging to include `shell/`.
- Added regression checks for identifier cleanup and stale refresh ownership.

Validation: all 107 nested-shell assertions passed (race 28, UI 47, preferences
26, large list 6). Shexli found 0 errors and 0 warnings, with one clipboard
manual-review finding. Schema validation, script syntax and diff checks passed.
Full results are recorded in `docs/VERIFICATION.md` §5. The provider-side
lock race remains documented as OTP-006; this refactor does not remove that
API limitation. A new login/logout check remains a manual host-session check.
